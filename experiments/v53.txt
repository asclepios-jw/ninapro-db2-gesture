================================================================
v53 — 실제(예측 기반) 분할 per-movement: 80.44%
       oracle 없이 격차의 49% 회수 — 정직한 배포 per-movement ≈ 80%
================================================================


[1] 계기
v51 oracle 반복 다수결 88%는 제스처 경계를 안다는 전제. v52 온라인 평활 78.6%.
남은 격차는 '분할'. 이 버전은 예측된 rest↔제스처 런으로 세그먼트를 직접 검출
(oracle 아님)하고 세그먼트 내 다수결로 라벨을 통일해 정직한 per-movement를 잰다.


[2] 방법 (추론 후처리, 재학습 0)
  1. 앙상블 윈도우 예측. rest=인코딩 0.
  2. 피험자 내 시간순: 예측 비-rest 런 = 검출 제스처 세그먼트.
     - 짧은 rest 간극(<=GAP)은 이어붙임(순간 rest 오탐 방지).
     - 짧은 비-rest 런(<MINLEN)은 rest로 폐기(오탐 제거).
  3. 각 검출 세그먼트를 그 안 다수결 라벨로 통일 → 프레임 예측 → acc/macroF1.
  GAP∈{1,2,3}, MINLEN∈{2,3,5} 스윕. 검출 세그먼트 수를 실제(1960)와 비교.


[3] 기대
검출이 실제 제스처 수에 가까우면(과/미분할 적으면) oracle에 근접.


[4] 결과
  기준 프레임: 73.00% / macroF1 0.6444 / hard 63.1%
  실제분할 최고 (GAP=2, MINLEN=5):
     acc 80.44% (+7.45p) / macroF1 0.7814 / hard 73.4%
     검출 2102 세그먼트 = 실제 1960의 1.07배 (과분할 7%뿐, 매우 정확)
  참조: v52 중심평활 78.64% / oracle 88.04%
  → oracle 격차의 49% 회수. v52 평활보다 우수 + 진짜 per-movement 출력.

  스윕 안정성: 모든 (GAP,MINLEN) 조합이 80.0~80.4%로 촘촘 → 견고.
  MINLEN↑(짧은 오탐 폐기)·GAP=2가 최적. 검출 세그먼트가 GT의 1.05~1.32x로
  약간 과분할이나 큰 문제 아님.


[5] 문제
없음. 분할이 예측만으로 이뤄져 oracle 사용 안 함(정직). 남은 80→88 격차의
원인: (a) 검출 경계 부정확, (b) 일부 세그먼트 다수결 오류(진짜 어려운 제스처),
(c) 검출 실패(놓침/분할).


[6] 배운 점
- 정직한 배포 per-movement ≈ 80% (검출+다수결). oracle 88%와 8p 차 =
  '경계를 정확히 아는 값어치'. hard도 73.4%로 프레임(63%)보다 크게 개선.
- 앙상블의 rest/제스처 예측만으로도 분할 품질이 좋음(검출 수 1.07x).
- 프레임 73%는 배포 시스템의 실제 성능이 아니다 — 최소한의 시간 처리(평활/분할)
  만으로 80%대. 보고 시 이 계층을 반드시 함께 제시해야 정직.


[7] 다음
남은 80→88 격차·프레임 73% 자체를 올리려면 '더 나은 기저 모델'이 필요.
→ v54: 근본적으로 다른 아키텍처(2D 시간-주파수 CNN) 앙상블 멤버로 프레임 천장
  돌파 시도. 프레임이 오르면 평활·분할·oracle 모두 비례 상승.
