================================================================
v3 — openclaw 실험 시작: "이 신호가 누구의 것인지 알려주자" + 불균형 보정
================================================================

[배경: 왜 별도의 openclaw 트랙이 생겼나]

v2까지의 결과(최고 64.14% 정확도)를 보고, v2의 두 가지 한계를 동시에 풀어보기 위해
사용자가 별도의 작업(openclaw 폴더, 별도 에이전트/툴)을 추가로 지시했다.
v2의 한계로 지목된 것은 다음 두 가지였다:

1) 40명 풀링 일반화의 어려움: 모델은 신호만 보고 "이게 어떤 동작인지"는 맞혀야 하는데,
   "이게 누구의 신호인지"는 전혀 모른 채 학습한다. 그런데 같은 동작이라도 사람마다
   신호 패턴이 다르므로, "누구의 신호인지"를 알면 동작 판별에 도움이 될 수 있다는 가설.
2) rest 클래스 불균형: rest(아무 동작도 안 하는 상태, 라벨 0)가 test set의 43.2%를
   차지한다. 이렇게 한 클래스가 절반에 가깝게 많으면, 모델이 "그냥 다 rest라고 찍어도"
   accuracy가 꽤 높게 나오는 함정에 빠지기 쉽고, 실제로 동작 클래스들을 잘 구분하는지는
   accuracy만 봐서는 알 수 없다 (그래서 macro-F1을 같이 보는 이유이기도 하다).


[아이디어 1: Subject-Aware Embedding (피험자 ID 임베딩)]

openclaw/models_v3.py의 SubjectAwareCNNLSTM 구조.

기존 CNN-LSTM(v1/v2)은 12채널 EMG 파형만 입력으로 받았다. v3는 거기에 "이 윈도우가
몇 번 피험자의 것인가"라는 정보를 추가로 넣어준다. 방법은 PyTorch의 nn.Embedding을
사용해서, 피험자 ID(1~40)를 32차원의 학습 가능한 벡터(emb_dim=32)로 변환하는 것이다.
이 임베딩 벡터는 처음엔 랜덤하지만, 학습이 진행되면서 "이 피험자는 신호가 대체로
이런 특성을 가진다"는 정보를 점점 담게 된다.

이 임베딩 벡터를 CNN이 뽑아낸 특징 맵의 모든 시간 스텝에 똑같이 이어붙인(concatenate)
다음 LSTM에 넣는다. 즉 LSTM은 "이 시점의 신호 특징 + 이 사람이 누구인지" 두 정보를
동시에 보고 다음 계산을 한다. 이렇게 하면 모델이 "사람마다 다른 패턴"을 미리 보정해서
판단할 수 있을 것이라는 기대였다.

왜 이런 구조가 말이 되는가: 사람 얼굴 인식에서 "이 사람이 누구인지"를 보조 정보로
주면 표정 변화에 덜 흔들리는 것과 비슷한 원리로, 피험자 ID를 명시적으로 주면 모델이
"이 사람 고유의 신호 특성"과 "동작 자체의 특성"을 분리해서 학습하기 쉬워질 수 있다는
아이디어다.


[아이디어 2: Focal Loss + Class Weight (클래스 불균형 보정)]

openclaw/train_cnn_v3.py, models_v3.py의 FocalLoss 클래스.

기존(v1/v2)에는 단순 CrossEntropyLoss를 썼는데, 이는 모든 클래스를 동등하게 취급하기
때문에 rest처럼 압도적으로 많은 클래스 쪽으로 모델이 편향될 위험이 있다. 이를 보정하기
위해 두 가지를 동시에 적용했다:

1) Class Weight: train 데이터에서 각 클래스가 등장한 빈도의 역수를 가중치로 사용
   (get_class_weights 함수). 즉 적게 등장하는 클래스의 손실(loss)에는 더 큰 가중치를,
   많이 등장하는 rest 같은 클래스에는 더 작은 가중치를 곱한다.
2) Focal Loss(gamma=2.0): 일반 CrossEntropy에 (1-pt)^gamma 항을 곱한 손실 함수.
   pt는 모델이 정답 클래스에 부여한 확률이다. 이미 모델이 잘 맞히고 있는("쉬운") 샘플은
   pt가 크므로 (1-pt)^gamma가 작아져서 손실 기여가 줄어들고, 아직 잘 못 맞히는("어려운")
   샘플은 손실 기여가 그대로 유지된다. 즉 "쉬운 문제는 그만 신경 쓰고 어려운 문제에
   집중하라"는 의도의 손실 함수.

당시 작성된 보고서(v3_improvement_report.md)는 이 조합을 "accuracy와 F1을 동시에
끌어올릴 수 있는 가장 실용적인 방법"이라고 설명했다. 의도 자체는 합리적으로 보였다.


[학습 설정]

- epochs=20, optimizer/scheduler는 기존과 유사한 구성.
- 체크포인트(가장 좋은 모델로 저장하는 기준)는 val_loss가 가장 낮을 때를 선택했다
  (best_val_loss = float('inf')로 시작해서 갱신).


[v3 결과 — 그리고 처음 드러난 이상 신호]

| 모델                         | Test Acc | Test Macro-F1 | rest(0) recall |
|------------------------------|----------|----------------|------------------|
| v3 (SubjectAware CNN-LSTM)   | 30.78%   | 40.29%         | 0.0001           |

v2의 CNN-LSTM이 64.14% accuracy였던 것에 비해 v3는 30.78%로 절반 이하로 폭락했다.
더 눈에 띄는 것은 rest(0) 클래스의 recall이 0.0001이라는 점이다. recall 0.0001은
거의 0이나 마찬가지로, "모델이 거의 rest를 예측하지 않는다"는 뜻이다. rest가 test
set의 43.2%를 차지하는데 이 클래스를 거의 못 맞히니 전체 accuracy가 크게 떨어진
것은 당연한 결과다.

이 시점에서는 "Focal Loss + Class weight를 같이 썼더니 rest 클래스를 거의 예측하지
않게 됐다"는 현상은 확인했지만, 정확히 두 메커니즘이 어떻게 상호작용해서 이런 극단적인
결과를 낳았는지는 아직 깊이 분석되지 않은 상태였다. v3 시점에서는 일단 "방향이
틀렸다기보다 무언가 다른 요인이 있을 것"이라 보고, 아키텍처를 더 발전시켜보면서
(v4, v5) 같은 손실 함수 설정을 그대로 유지한 채 추가 실험을 이어갔다.
(돌이켜보면 이 시점에 바로 손실 함수 쪽을 의심하고 멈췄어야 했지만, 아키텍처
개선과 손실 함수 문제가 동시에 진행되어 원인 파악이 v6 시점까지 늦어졌다 — 이
지연 자체도 기록해둘 만한 시행착오다.)

[학습 중 예상치 못하게 발생한 문제들 — 버전/환경/하드웨어]

이 버전부터는 별도 에이전트(openclaw)가 자체 conda 환경(med-ai)에서 작업을
진행했다 — 메인 파이프라인(code/ 폴더)과는 분리된 실행 환경이다. 이번에는
패키지 버전 충돌 같은 명백한 환경 문제는 없었지만, 서로 다른 환경에서 작업이
진행되면 "어느 쪽 결과가 최신이고 신뢰할 수 있는지"를 헷갈리기 쉽다는 잠재적
위험은 있었다 (실제로 나중에 폴더 이름이 겹쳐서 결과 위치 사고가 한 번 났다 —
v6 이후 정리 단계의 일이라 별도로 기록).

기술적으로 작은 버전 이슈 하나는 있었다: 학습이 끝난 뒤 체크포인트를 불러오는
코드(model.load_state_dict(torch.load(...)))가 PyTorch의 기본 동작
(weights_only=False)을 그대로 썼는데, 이는 향후 PyTorch 버전에서 기본값이
바뀔 예정이라는 FutureWarning을 띄운다(신뢰할 수 없는 pickle 파일을 불러올 때
임의 코드가 실행될 수 있다는 보안 경고와 관련). 학습 결과 자체에는 영향이
없었지만, 이후 버전에서 안전하게 고쳐야 할 부분으로 남겨뒀다(v5에서 실제로
weights_only=True로 수정됨).

진짜 "예상치 못한 문제"는 기술적인 게 아니라 분석 속도였다: rest recall이
0.0001이라는 극단적인 숫자가 v3에서 이미 나왔는데, 이 시점에는 "왜 이런 숫자가
나왔는지"를 깊게 분석하지 않고 일단 다음 아키텍처 실험(v4)으로 넘어갔다.
돌이켜보면 이 신호 하나만으로도 손실 함수를 의심할 충분한 근거가 있었다.
즉 "이상한 결과가 나왔을 때 바로 원인 분석에 들어가지 않고 다음 실험으로
넘어간 것" 자체가 이 프로젝트에서 가장 비용이 컸던 시행착오의 시작점이다
(v6에서 결국 원인이 밝혀지기까지 v4, v5 두 버전의 학습 시간을 추가로 썼다).


[이 버전에서 다음 버전으로 넘어가게 된 이유 — 요약]

1. accuracy/F1 폭락의 원인이 아직 명확하지 않은 상태에서, "피험자 임베딩 자체의 효과를
   더 끌어올리면 불균형 문제를 상쇄할 수 있지 않을까"라는 가설로 attention pooling을
   추가한 v4로 넘어갔다. (결과적으로는 잘못된 방향의 시도였다는 것이 v6에서 드러난다.)
