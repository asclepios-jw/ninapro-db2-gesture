v51 — 반복(제스처 실행) 단위 다수결 평가: 88.04% / macro-F1 0.8457
       macro-F1 0.64는 '신호 상한'이 아니라 '윈도우 레벨 착시'였다
================================================================


[1] 이 버전을 시작한 계기

외부 검토(MiniMax) A3: "macro-F1 신호 상한" 결론(v49 후처리+v50 재균형 실패)이
성급하다. 윈도우 레벨 macro-F1(0.644)은 경계 윈도우 노이즈로 과소평가일 수
있으며, Ninapro 표준인 '반복 단위(제스처 실행) 다수결'로 평가하면 gesture
레벨 성능이 나온다. → 모델 불변, 지표만 바꿔 착시 여부 검증.


[2] 방법

추론 후처리만 (재학습 0):
  1. v48 최적 8모델 앙상블의 윈도우 예측(확률 평균 argmax) 계산.
  2. test(rep6)를 저장 순서(피험자 내 시간순)대로 순회 → 연속된 동일
     (subject, label) 런 = 제스처 실행 인스턴스로 묶음.
  3. 인스턴스별 윈도우 예측 다수결 → 인스턴스당 예측 1개.
  4. 인스턴스 레벨 acc/macro-F1/hard·easy 계산, 윈도우 레벨과 비교.

그룹핑 검증: 108,171 윈도우 → 3,920 인스턴스 (평균 27.6 윈도우/인스턴스).
  27.6 × 3920 ≈ 108,192 ≈ 전체 윈도우 → 그룹핑 정확(누락/중복 없음).


[3] 기대했던 효과

경계/onset/offset 윈도우의 일시적 오분류(주로 rest로 새는 것)가 다수결로
상쇄되면 gesture 레벨 성능이 오를 것. 얼마나 오르는지가 A3(착시 vs 상한)를
판가름.


[4] 결과 — A3 확정(착시), 큰 폭 상승

  지표            윈도우 레벨   반복 단위     변화
  ──────────────  ──────────   ──────────    ────────
  전체 acc        73.00%       88.04%        +15.04p
  macro-F1        0.6444       0.8457        +0.2013
  제스처 macroF1  0.6446       0.8477        +0.2030
  hard acc        63.14%       83.88%        +20.73p
  easy acc        74.40%       88.63%        +14.23p

**판정: macro-F1이 0.64 → 0.85로 급등 → '윈도우 레벨 착시' 확정.**
  낮은 윈도우 macro-F1은 신호 판별력 한계가 아니라, 제스처 실행 안의
  경계/약활성 윈도우가 순간적으로 rest로 분류되며 frame 단위 recall을
  깎은 것. 그 오류는 실행 내에서 소수라 다수결로 사라진다.
  → v49/v50의 "재균형 실패 = 신호 상한" 결론에서 '상한' 부분은 틀렸다.
    (재균형이 안 먹힌 건 맞지만, 그 이유는 상한이 아니라 '단위' 문제였다.)

hard도 63→84%로 +20.73p → hard의 낮음도 상당 부분이 frame 단위 착시.


[5] 학습 중 예상치 못하게 발생한 문제들

없음(추론 후처리). 그룹핑이 저장 순서(피험자 내 시간순) 가정에 의존 —
build_dataset_v28가 피험자별·stride 순서로 윈도우를 쌓으므로 성립. 인스턴스
수·윈도우합 검증으로 확인.


[6] 이번 버전에서 배운 점

**평가 단위가 결론을 바꾼다 — 우리는 3버전(v49/v50/이전 진단) 동안 잘못된
  단위로 macro-F1을 판단했다.**
  frame(윈도우) 레벨과 movement(반복) 레벨은 다른 질문이다:
    - 윈도우 레벨 73%/0.644 = "실시간 프레임 정확도"(분할 정보 없음, 더 엄격).
    - 반복 레벨 88%/0.846 = "제스처 단위 분류 정확도"(Ninapro 표준, 문헌 비교용).
  둘 다 정당하나 답하는 질문이 다르며, 문헌·발표에서 흔히 쓰는 건 후자.

**★ 중요한 정직성 caveat: 반복 단위는 ground-truth 분할을 가정한다.**
  인스턴스 경계를 '실제 라벨 런'으로 정의했으므로, 이 88%는 "제스처가 언제
  시작/끝나는지 안다"는 전제(oracle segmentation) 위의 수치다. 이는 Ninapro
  'per-movement' 표준 프로토콜과 동일하나, 연속 스트리밍 배포에선 별도의
  onset/segmentation이 필요하다. → 두 수치를 함께, 전제를 명시해 보고할 것.

**외부 검토의 가치 입증.**
  MiniMax A3 단일 지적이 프로젝트 성능 서사를 크게 바꿨다(73%가 아니라
  표준 프로토콜로 88%). 자기 검토로는 놓친 '평가 단위' 사각지대.
