================================================================
v15 — v14의 사후 추정을 실제 학습으로 검증: 가설이 그대로 확인됨
================================================================

[이 버전을 시작한 계기]

v14는 "기존 50클래스 v8 모델의 예측 결과를 사후에 그룹으로 묶어서 평가"한
진단이었다. 클래스를 단순화하면 어려운 피험자의 격차가 줄어든다는 신호를
봤지만, 이건 추정일 뿐이었다 — 모델이 애초에 10개 클래스만 구분하도록
학습된 게 아니라 50개 클래스를 학습한 결과를 사후에 재해석한 것이기
때문이다. v15는 이 추정이 실제 학습으로도 재현되는지 직접 검증했다.


[방법: code/train_cnn_v15.py]

v14에서 계산해둔 k=10 클러스터 할당(cluster_assignment, 50개 원본 클래스
→ 10개 상위 클래스)을 그대로 가져와서, v8과 똑같은 데이터(data_processed/v8,
24채널)와 똑같은 아키텍처(SubjectAwareCNNLSTMAttention)와 똑같은 학습
레시피(CE+label_smoothing, AdamW, cosine, epoch 30, patience 6, val
macro-F1 체크포인트)로 라벨만 10개 상위 클래스로 바꿔서 처음부터 다시
학습시켰다.

라벨 매핑 시 주의할 점이 있었다: data_processed/v8의 y_train 등은 0~49
연속된 값이 아니라 원래 라벨 오프셋(0-17, 35-57, 81-89)을 그대로 담고
있다. v14의 cluster_assignment는 LabelEncoder로 0~49 연속 인코딩한 뒤의
순서를 기준으로 계산된 것이므로, 먼저 같은 LabelEncoder로 인코딩한 뒤에
cluster_assignment로 매핑해야 한다 — 이 순서를 빠뜨리면(원본 라벨 값을
바로 인덱싱하면) 배열 범위를 넘어가는 에러가 난다(실제로 처음 실행 시
이 에러가 났고, LabelEncoder 단계를 추가해서 수정했다).


[재현 정보]

  cd ninapro_db2_project/code
  python3 train_cnn_v15.py
  # CLUSTER_ASSIGNMENT = results/v14/class_grouping_results.json의 k10 항목
  # DATA_DIR = data_processed/v8 (재구축 없음, 라벨만 재매핑)
  # OUT_DIR  = results/v15


[비용 원장: 시간/디스크/GPU]

  데이터셋 디스크   : 추가 없음 (v8 데이터 재사용, 라벨만 메모리상에서 재매핑)
  결과물 디스크     : results/v15, best_model_v15.pth + report.txt +

                      동일하니 당연한 결과)
  GPU 메모리        : 정확히 측정하지 않음, v8과 비슷한 수준으로 추정


[결과]

  어려운 5명 acc     78.75%                79.27%           +0.52p
  나머지 35명 acc    86.94%                86.99%           +0.05p

  수가 달라 직접 비교 불가 — 참고용으로만 기록)


[기대와 실제가 어떻게 달랐는가]

기대: v14의 사후 추정이 "대략적인 방향"만 맞고 실제 학습에서는 차이가
있을 수 있다고 예상했다 — 사후 그룹화와 처음부터 그렇게 학습하는 것은
모델이 최적화하는 손실 함수 자체가 다르기 때문이다(50클래스 CE로 학습한
모델이 우연히 상위클래스 경계에서도 잘 작동하는 것과, 10클래스 CE로
직접 학습해 그 경계를 손실 함수가 직접 최적화하는 것은 이론적으로 다를
수 있다).

실제: 거의 차이가 없었다 — 모든 지표에서 v14 추정과 0.1~0.5%p 이내로
일치했고, 오히려 실제 학습이 추정보다 살짝 더 좋았다(격차가 0.47p 더
좁아짐). 이는 두 가지를 시사한다: (1) v8 모델이 50클래스를 학습하면서도
이미 상위클래스 수준의 구조를 충분히 잘 포착하고 있었다는 것, (2) 그래서
"처음부터 10클래스로 학습"이 주는 추가적인 이점은 크지 않았다는 것 — 즉
v14의 사후 추정 방법론 자체가 이번 케이스에서는 꽤 신뢰할 만한 근사였다는
뜻이다.

confusion matrix를 보면 한 가지 부작용도 발견됐다: 클러스터 9(클러스터링
결과 가장 큰 그룹, train 윈도우 약 30만 개로 다른 클러스터의 2~20배)가
다른 클러스터들의 오분류를 빨아들이는 "흡수 클래스"처럼 작동한다 —
나머지 9개 클러스터 모두 클러스터 9로 새는 비율이 0.15~0.35로 꽤 높다.
클러스터 9 자신은 recall 0.94로 매우 높지만, 이건 클러스터 9가 원래
다양한 동작들을 뭉뚱그린 크고 이질적인 그룹이라 "잘 맞히기 쉬운" 것일
수도 있다 — 클러스터링이 균등한 크기로 묶이지 않은 부작용으로 보인다.


[학습 중 예상치 못하게 발생한 문제들 — 버전/환경/하드웨어]

라벨 인코딩 순서를 빠뜨려 IndexError가 한 번 났다(위 [방법] 섹션에 기록).
원본 라벨이 0-49 연속이 아니라는 사실은 이미 v1 시점에 한 번 발견하고
문서화했었는데(RandomForest 리포트의 라벨이 이상하게 보였던 사건), 그
사실을 v15 코드를 짤 때 깜빡하고 놓쳤다가 실행 에러로 다시 상기하게 됐다
— "한 번 해결한 문제도 시간이 지나면 다시 같은 실수를 할 수 있다"는,
project 차원의 교훈을 다시 한번 확인한 사례. 다행히 에러가 명확한
IndexError로 즉시 드러나서 (조용히 잘못된 결과를 내는 대신) 바로 잡을 수
있었다.

하드웨어 자원 문제는 없었다 — v8과 동일한 규모라 RTX 2070 8GB로 문제없이
끝까지 돌았다.


[v1~v15 전체를 관통하는 결론]

v15는 v9~v13의 음성/무효 결과들과 달리, v14에서 본 부분적 긍정 신호를
**실제 학습으로 검증해 재확인한** 첫 사례다. 다만 이 결과를 메인 순위표
(v1~v11)에 그대로 끼워 넣지는 않는다 — v15는 50클래스가 아니라 10개
상위 클래스를 푸는 다른(더 쉬운) 문제이기 때문에, accuracy/macro-F1
숫자를 같은 줄에 놓고 비교하면 오해를 부른다. 대신 "클래스를 단순화하면
어려운 피험자의 격차가 실제로 줄어든다"는 사실 자체가 이번 버전의 핵심
산출물이다.

남은 질문은 "그래서 실제 서비스에서는 어떻게 쓸 것인가"다 — 50개 동작을
다 구분해야 하는 응용이라면 v15는 그 자체로 최종 답이 될 수 없고(클래스
수가 다르므로), 다음 단계(예: 큰 분류기로 먼저 상위클래스를 맞히고 그
안에서 작은 분류기로 세부 클래스를 다시 맞히는 2단계 구조)가 필요하다.


[향후 개선 후보 (v15 시점까지 미착수)]

- (핵심) 2단계 계층적 분류기: 1단계는 v15처럼 10개 상위클래스를 맞히고,
  2단계는 각 상위클래스 내부에서 원래 세부 클래스를 다시 분류하는 구조.
  어려운 피험자에게 상위클래스 단계의 이득이 세부 단계까지 이어지는지 확인.
- 클러스터 9(거대 흡수 클래스) 문제 완화 — 클러스터링 시 클러스터 크기를
  더 균등하게 맞추는 제약 추가, 혹은 거대 클러스터만 한 번 더 세분화.
- 클러스터 수(k)를 더 세밀하게 스캔(5~35)해서 어려운 피험자 격차와
  전체 정확도 사이의 최적 지점 찾기.
- "남은 격차"(v15에서도 7.72p)의 원인을 더 분석 — 클래스 단순화로도
  안 줄어드는 부분이 정확히 무엇인지.
- 도메인 적응(DANN, MMD) — 클래스 단순화와 결합 가능.
- 40명 개별 모델 학습 후 평균 정확도로 baseline(82.7%)과 진짜 동일 조건 비교
  (v9부터 계속 미뤄지는 항목).
