================================================================
v5 — "특징 추출기를 더 강하게": ResNet1D 백본으로 교체
================================================================

[이 버전을 시작한 계기]

v4까지 시도한 attention pooling은 v3 대비 아주 미세한 개선만 가져왔다(accuracy
+1.58p 정도). 이 정도로는 v2 수준(64.14%)을 회복하기에도 한참 부족했다. 그래서
"특징을 뽑아내는 부분(backbone) 자체가 너무 단순한 게 아닐까"라는 의심으로,
v1~v4에서 공통으로 쓰던 얕은 2단 Conv1d 구조를 더 깊고 강력한 ResNet1D 구조로
교체해보기로 했다.


[구조 설명: openclaw/models_v5.py]

ResNetLSTM 클래스. 핵심은 이미지 분류에서 널리 쓰이는 ResNet의 핵심 구성요소인
"Residual Block(잔차 블록)"을 1D 신호용으로 옮겨온 것이다.

ResBlock1D 동작 방식:
- Conv1d → BatchNorm → ReLU → Conv1d → BatchNorm을 거친 결과에, 입력을 그대로
  더해주는(혹은 채널/길이가 안 맞으면 1x1 conv로 맞춰서 더해주는) "skip connection"이
  있다. 즉 출력 = (블록이 새로 계산한 변화량) + (원래 입력).
- 왜 이런 구조가 깊은 네트워크에 유리한가: 일반적인 깊은 CNN은 층을 쌓을수록
  학습이 어려워지는(기울기 소실 등) 문제가 있는데, skip connection이 있으면 모델이
  "굳이 새로운 특징을 안 만들고 입력을 그대로 통과시켜도 되는" 선택지가 항상 열려있어
  학습이 훨씬 안정적이다.

이 프로젝트의 ResNetLSTM은 다음 순서로 구성된다:
  Conv1d(stride=2) + BN + ReLU + MaxPool  →  ResBlock(64→64)  →  ResBlock(64→128, stride=2)
  → ResBlock(128→256, stride=2)  →  (피험자 임베딩 결합)  →  LSTM  →  Attention(v4와 동일)  →  분류기

v1~v4의 2단 Conv1d(64→128, 채널 수 최대 128)에 비해, v5는 3단 ResBlock을 거쳐 최종
채널 수가 256까지 늘어나고, 중간에 stride=2를 두 번 더 적용해 시간 축도 더 많이
압축한다. 즉 표현력(capacity) 자체는 v1~v4보다 훨씬 크다.
Dropout도 0.4 → 0.5로 한 번 더 늘렸다 (모델이 더 커진 만큼 과적합 방지를 강화).

손실 함수와 체크포인트 기준은 v3/v4와 동일하게 유지: FocalLoss(gamma=2.0) + class
weight, val_loss 최저 기준 체크포인트 선택. (즉 이번에도 "의심되는 손실 함수는
그대로 두고 아키텍처만 바꿔서" 테스트한 것.)


[v5 결과]

| 모델                              | Test Acc | Test Macro-F1 | rest(0) recall |
|-----------------------------------|----------|----------------|------------------|
| v5 (+ResNet1D 백본)               | 33.13%   | 43.21%         | 0.0002           |

v4(32.36% / 42.34%)보다 또 약간 개선되었지만(+0.77p, +0.87p), 여전히 v2(64.14%)에는
한참 못 미치고, rest recall도 그대로 0.0002로 거의 변화가 없다. 즉 백본을 훨씬
강력한 ResNet1D로 바꿔도 rest를 거의 예측하지 않는 문제는 전혀 풀리지 않았다.


[재현 정보]

  conda activate med-ai
  cd ninapro_db2_project
  python3 openclaw/train_cnn_v5.py
  # DATA_DIR = data_processed/v2 (v3/v4와 동일 데이터 재사용)

[비용 원장: 시간/디스크/GPU — 예상과 달랐던 부분]

  데이터셋 디스크   : 추가 없음 (v2~v4와 동일 데이터)
  결과물 디스크     : openclaw/results_v5, 5.2MB
  학습 시간         : 약 1,603s (20 epoch 합계, epoch당 일정하게 약 80s)
  GPU 메모리        : 정확히 측정하지 않음

  여기서 가장 예상과 달랐던 부분: ResNet1D 백본을 추가해 "더 무거운" 모델인데도,
  v3(epoch당 142~316s)나 v4(epoch당 약 320s)보다 학습이 4배 가까이 더 빨랐다
  (epoch당 약 80s). 추정되는 이유는, ResNet 쪽 구조가 stride=2 conv를 여러 번
  거치면서 LSTM에 넘기기 전 시퀀스 길이를 v3/v4보다 훨씬 짧게 줄여놓기 때문에,
  파라미터 수는 늘었어도 LSTM이 실제로 처리해야 하는 시간 스텝 수가 줄어 전체
  연산량은 오히려 작아진 것으로 보인다. "모델이 더 복잡해 보인다고 반드시 더
  느려지는 것은 아니다"라는, 비용 측면에서의 직관적이지 않은 교훈이다.


[학습 중 예상치 못하게 발생한 문제들 — 버전/환경/하드웨어]

v5에서는 v3/v4에 있던 torch.load FutureWarning이 더 이상 나타나지 않았다 —
모델 로딩 코드에 weights_only=True를 추가해서 고쳤기 때문이다. 다만 이걸
"의도적으로 고쳤다"기보다는 코드를 다시 정리하면서 같이 반영된 것이라, 정확히
언제·왜 고쳤는지가 별도로 기록되지는 않았다. 작은 일이지만 "경고/버그 수정을
했다면 그 사실 자체를 기록해두지 않으면 나중에 왜 사라졌는지 추적하기 어렵다"는
교훈이 된다.

ResNet1D 백본을 추가하면서 모델 파라미터 수와 GPU 메모리 사용량이 v1~v4보다
늘었지만, RTX 2070 8GB 한도 안에서는 여전히 문제없이 학습됐다. 하드웨어 자원
문제는 없었다.

기대와 실제가 갈린 지점: "더 강력한 특징 추출기(ResNet)를 쓰면 attention만으로는
부족했던 표현력을 보완해서 의미 있게 좋아질 것"이라고 기대했지만, 실제 개선은
+0.77p에 불과했다. v3→v4→v5 세 버전 모두 비슷하게 작은 개선만 있었다는 패턴
자체가, "아키텍처가 아니라 공통으로 깔려있는 다른 요인(손실 함수)이 진짜
원인"이라는 결론으로 이어진 핵심 증거가 됐다 — 즉 이 버전에서 "기대만큼 안
됐다"는 사실이 그 자체로 가장 중요한 발견이었다.


[v3 → v4 → v5 전체를 돌아본 결론]

세 버전(v3/v4/v5)에 걸쳐 아키텍처는 계속 강화했다(임베딩만 → +attention → +ResNet
백본까지). 그런데 accuracy는 30.78% → 32.36% → 33.13%로 거의 제자리걸음에 가까운
미세한 개선만 있었고, rest recall은 세 버전 모두 0.0001~0.0002 수준으로 변화가
없었다. 이는 "아키텍처가 문제가 아니다"라는 강한 증거였다. 세 버전 모두 공통으로
가지고 있던 것은 단 하나, FocalLoss + inverse-frequency class weight + val_loss
기준 체크포인트 선택이었다. 이 지점에서 비로소 "아키텍처를 그만 바꾸고, 손실
함수 자체를 의심하고 점검해야 한다"는 결론에 도달했다.


[이 버전에서 다음 버전으로 넘어가게 된 이유 — 요약]

1. 세 가지 다른 아키텍처(v3/v4/v5)에서 모두 거의 동일하게 rest recall이 붕괴되는
   패턴이 반복됐다는 사실은, 변수를 하나씩 통제하며 비교하는 가장 직접적인 디버깅
   증거가 되었다 — 아키텍처가 아니라 모든 버전에 공통으로 들어있던 손실 함수 설계가
   원인이라는 결론.
2. v6에서는 아키텍처(v4 기준: SubjectAware + Attention)는 그대로 유지한 채, 의심되는
   손실 함수와 체크포인트 선택 기준만 바꿔서 "정말 손실 함수가 원인이었는지"를
   검증하기로 했다.
