## 5. E3 `.mat` 파일 row 불일치 버그 (중요)
- **증상**: `data_utils.normalize_per_subject()` 추가 후 `IndexError: boolean index did not match indexed array along axis 0` (emg 5,238,693행 vs reps 5,238,692행).
- **원인 분석**: 피험자 1의 E3 파일(`S1_E3_A1.mat`)에서 `emg`는 877,073행인데 `restimulus`/`rerepetition`은 877,072행으로 원본 데이터 자체에 1행 어긋남이 있음 (다운로드 데이터의 결함으로 추정).
- **조치**: `load_subject_raw()`에서 각 exercise 파일 로딩 시 `min(len(emg), len(labels), len(reps))`로 3개 배열을 공통 길이로 truncate하도록 방어 코드 추가.
- **검증**: 수정 후 subject 1 재처리 → 정상 동작 확인 (윈도우 수 26,192 → 동일하게 유지, 영향 거의 없음).

## 6. RandomForest 모델 파일 50.6GB
- **증상**: v1 RandomForest(`max_depth=None`, n_estimators=300)을 70만 샘플로 학습한 결과 `rf_model.joblib`이 50.6GB로 저장됨.
- **원인**: 트리 깊이 제한이 없어 다수 트리가 과도하게 깊게(리프마다 거의 단일 샘플까지) 자람.
- **조치**: v2에서 `max_depth=20`으로 제한 → 모델 용량 13.5GB (73% 감소). 단, test accuracy가 65.88%→61.08%로 소폭 하락하는 트레이드오프 발생.
- **미해결**: v1의 50.6GB 파일은 현재도 `results/v1/rf_model.joblib`에 남아있음 — 삭제 여부는 사용자 확인 필요 (디스크 삭제는 되돌릴 수 없어 임의 삭제하지 않음).

## 7. 피험자별(per-subject) 정규화 도입과 혼재된 효과
- **배경**: 사용자가 "성능이 안 좋다"고 지적 → 원인 분석 결과 40명 풀링 시 피험자 간 EMG 진폭 차이가 글로벌 정규화로는 보정되지 않는 점을 지목.
- **조치**: 각 피험자 본인의 train-rep(1~4) 통계로 z-score 정규화하도록 `data_utils.normalize_per_subject()` 추가, 데이터셋 재빌드(v2).
- **결과**: CNN1D/CNN-LSTM은 개선(+1~3p), RandomForest는 오히려 악화(-2~5p). RF는 max_depth 제한과 정규화 변경이 동시에 들어가 두 원인이 섞여 단독 효과 분리가 어려움 — 후속 분석 필요.

## 8. "82.7% vs 60%대" 비교 질의 — 문제 정의 차이 설명
- 사용자가 기존 단일 피험자 결과(82.7%)와 신규 40명 풀링 결과(~60-64%)를 같은 기준으로 비교하며 성능 저하로 오인.

- 진짜 동일 조건 비교를 위해서는 40명 각각 개별 모델을 학습해 평균을 내야 함 — 아직 미착수, 향후 과제로 기록.

## 10. openclaw v3~v5 — FocalLoss + class weight 중첩으로 rest 클래스 붕괴 (중요)
- **배경**: 사용자가 `openclaw`(별도 에이전트/툴)에 v2 개선을 추가로 지시. v3~v5는 피험자 ID 임베딩 + attention + ResNet1D로 아키텍처를 발전시켰고, 클래스 불균형 보정으로 `FocalLoss(gamma=2.0)` + train 분포 역수 기반 class weight를 함께 적용.
- **증상**: 보고서(`v3_improvement_report.md`)는 "accuracy와 F1을 동시에 끌어올리는 실용적 방법"이라 주장했지만, 실측 `test_metrics.txt`는 정반대 — accuracy가 v2의 64.14%에서 30.78~33.13%로 붕괴, rest(0) 클래스 recall이 0.0001~0.0002.
- **원인 분석**: rest가 train의 약 43%를 차지해 inverse-frequency 가중치가 rest에 극단적으로 작은 값을 부여. 여기에 FocalLoss의 `(1-pt)^gamma`가 "이미 잘 맞히는(쉬운) 샘플"의 손실을 추가로 깎는데, rest는 원래 분류하기 쉬운 클래스라 이중으로 억제됨 → 모델이 rest를 거의 예측하지 않는 방향으로 수렴. 체크포인트 선택을 `val_loss` 최저 기준으로 한 것도 이 왜곡된 손실 지형에서 잘못된 지점을 고르게 만든 부차 원인.
- **조치**: 아키텍처(피험자 임베딩 + attention, v4 기준)는 그대로 유지하면서 손실 함수만 `CrossEntropyLoss(label_smoothing=0.1)`로 교체하고, 체크포인트 선택 기준을 `val macro-F1`로 변경한 v6를 새로 작성 (`openclaw/models_v6.py`, `openclaw/train_cnn_v6.py`).
- **결과**: test accuracy 67.79%, macro-F1 55.99% — v2(64.14%/48.48%) 대비 개선, 지금까지 만든 모든 모델 중 최고 성능. 피험자 임베딩 아이디어 자체는 유효했고, 손실 함수 버그가 그 효과를 가리고 있었음이 확인됨.
- **교훈**: 클래스 불균형 보정 기법(class weight, focal loss)을 여러 개 동시에 강하게 적용하면 서로 상쇄가 아니라 중첩되어 역효과를 낼 수 있음. 적용 후 반드시 다수 클래스의 recall과 전체 accuracy를 함께 확인해야 함.

## 12. v8 — "파라미터 튜닝은 70%대 초반이 한계" 판단 후 전처리 재설계
- **배경**: 사용자가 (다른 세션에서) 파라미터 튜닝만으로는 70%대 초반이 한계라고 판단, 전처리 쪽에 더 시도해볼 게 있는지 논의 후 1) 윈도우/스텝 크기 비교, 2) rectification/RMS envelope 채널 추가, 3) 윈도우 경계 라벨 다수결 개선, 이 순서로 진행하기로 함.
- **순서 조정**: 1번(윈도우 크기)과 3번(경계 라벨)을 분리하면 효과가 섞여 해석이 어려워질 수 있어, 두 변경을 한 세트로 같이 스윕하고 envelope 채널 추가(2번, 모델 입력 채널 변경이 필요해 가장 비용이 큼)는 마지막에 적용하도록 순서를 바꿔 진행.
- **1단계 (스윕)**: 8명 피험자 부분집합 + RandomForest(빠른 proxy)로 윈도우 길이(150/200/300ms) x 라벨 순도 필터(0.0/0.8) 6개 조합 비교. 결과: 윈도우가 길수록, 순도 필터를 걸수록 일관되게 개선 → 300ms/150ms + purity≥0.8 확정 (val acc 70.49%, macro-F1 62.30%, 부분집합 기준).
- **2단계 (전체 재구축)**: 확정된 설정으로 40명 전체 재구축 (`data_processed/v3/`, 19.1GB).
- **3단계 (envelope 채널)**: `compute_envelope()`(정류+10Hz 저역통과)로 12채널 envelope을 raw 12채널에 추가해 24채널로 확장, v6와 동일한 SubjectAware+Attention 아키텍처로 학습 (`data_processed/v8/`, 38.3GB).
- **결과**: test accuracy 68.69%, macro-F1 56.92% — v6(67.79%/55.99%) 대비 +0.90p/+0.93p 개선. 방향은 맞았으나 v5→v6의 개선폭(+7.51p)에 비하면 작음.
- **해석**: 전처리 개선의 여지가 있다는 판단은 맞았지만, v6 시점에 이미 이 데이터/모델 조합의 성능 상한 근처에 도달해 있었던 것으로 보임. 이후 더 큰 개선을 보려면 전처리/구조보다는 라벨-EMG 시차 보정이나 피험자별 fine-tuning 같은 더 근본적인 변경이 필요할 가능성.

## 13. v9 — 라벨-EMG 시차 보정(가설 반증) + 피험자별 Fine-tuning
- **배경**: v8까지도 개선폭이 계속 줄어들어, "파라미터/전처리 튜닝은 한계, 더 근본적인 접근 필요"로 판단. 단일 피험자 baseline(82.7%)과의 격차(14p)를 메우려고 (1) 라벨-EMG 시차 보정, (2) 피험자별 fine-tuning 두 가지를 동시에 진행.
- **시차 보정 결과 — 가설 반증**: `apply_label_delay()`로 라벨 타임라인을 delay_ms만큼 지연시켜 8명 부분집합+RandomForest로 0~250ms 스윕한 결과, **delay=0(보정 없음)이 1위**였고 지연을 늘릴수록 일관되게 나빠졌다. 원인으로 추정되는 것: 우리가 쓰는 `restimulus`는 NinaPro가 이미 실제 동작 타이밍에 맞춰 보정해놓은 라벨(raw `stimulus`가 아님)이라, 추가 보정을 얹으면 이미 맞춰진 정렬을 다시 깨뜨리는 역효과만 났다. **교훈**: "직관적으로 타당해 보이는 가설"도 데이터 자체의 전처리 히스토리를 먼저 확인하지 않으면 헛수고가 될 수 있다 — 이 방향은 막힌 길로 분류하고 재시도하지 않기로 함.
- **Fine-tuning 결과**: v8 pooled 체크포인트를 베이스로 40명 각각 본인 train 데이터(~11,000 윈도우)로 짧게 추가 학습 후 본인 test로 평가, 평균 acc 68.68%→69.07%(+0.39p), macro-F1 57.84%→58.78%(+0.94p). 개선은 작았지만 **피험자 간 분산(std_acc 7.56%p)이 평균 개선폭보다 훨씬 컸다** — 일부는 +1%p 이상 좋아지고 일부는 -1%p 이상 나빠짐.
- **가장 중요한 발견**: fine-tuning과 무관하게, 일부 피험자(S01, S05, S40)는 **풀링 모델만으로도 이미 단일 피험자 baseline(82.7%) 수준**이었고, 반대로 일부(S28, S31)는 fine-tuning을 해도 60%를 못 넘겼다. 즉 "40명 평균 정확도"라는 숫자 하나로는 보이지 않던, 피험자별로 풀링의 유불리가 극명하게 다르다는 사실이 처음으로 명확히 드러났다.
- **작업 효율화 사례**: 원래 계획은 "시차 보정값 확정 → 40명 전체 재구축 → 학습"이었으나, 스윕에서 delay=0이 1위로 나오자 재구축 단계를 건너뛰고 v8 데이터셋을 그대로 재사용했다. 계획을 끝까지 기계적으로 따르지 않고 중간 결과에 따라 불필요한 단계를 즉시 생략한 사례.

## 14. v10 — Freeze 강도 어블레이션, "과적합 때문"이라는 가설 기각
- **배경**: v9의 분산(std_acc 7.56%p)을 보고 (다른 세션에서) "피험자당 데이터가 적은데 전체 네트워크를 다 풀어서 fine-tuning하면 과적합으로 분산이 커진다, CNN을 얼리고 classifier/attention만 학습하면 더 안정적일 것"이라는 가설이 제시됨. 같은 자리에서 Center Loss/Focal Loss 튜닝도 제안됐으나, 사용자가 이번엔 freeze 가설 하나만 먼저 검증하기로 결정.
- **검증 설계**: v9와 완전히 동일한 설정(데이터, epoch, lr)에서 학습 가능 파라미터 비율만 다르게 한 두 모드(classifier_only 1.6%, freeze_cnn 96%)를 v9(100%)와 비교 — 변수 하나만 바꿔 순효과를 보려는 설계.
- **결과 — 가설 기각**: classifier_only(가장 강하게 얼림)는 fine-tuning 안 한 것보다도 더 나빴고(68.36% < 68.68%), freeze_cnn(96%)은 v9(100%)와 평균·표준편차가 거의 완전히 일치(69.10% vs 69.07%, std 7.56%p vs 7.56%p). 즉 freeze 정도를 조절해도 분산이 전혀 줄지 않았다.
- **결론**: v9에서 본 분산은 과적합 때문이 아니라, 피험자 본인의 신호 자체가 원래 쉽거나 어렵다는 데이터 쪽 근본 차이다. 어느 학습 전략을 쓰든 같은 피험자(S01/S05/S40은 항상 잘됨, S28/S31은 항상 안 됨)가 반복됐다.
- **예상치 못했던 부분**: classifier_only는 학습 파라미터가 freeze_cnn의 60분의 1(12,850 vs 772,434)인데도 학습 시간은 절반 정도(885s vs 1622s)밖에 안 줄었다. forward pass(전체 네트워크를 통과시키는 연산)는 freeze 여부와 무관하게 동일하게 수행되기 때문 — "파라미터를 적게 학습한다고 그 비율만큼 시간이 준다"는 직관이 틀렸다는 것을 확인.
- **교훈**: 두 가지 전략(freeze, Center/Focal Loss)이 같이 제안됐을 때 하나씩 분리해서 검증한 것이 옳은 선택이었다 — 만약 둘을 동시에 적용했다면 "분산이 줄었다 / 안 줄었다"의 원인을 freeze와 loss 중 어느 쪽인지 가릴 수 없었을 것이다.

## 15. v11 — Center Loss 적용, 안전했지만 무효과
- **배경**: v10에서 분산 문제가 과적합이 아님을 확인한 뒤, 같이 제안됐던 두 번째 전략(Center Loss/Focal Loss로 클래스 경계 보강)을 시도. v3~v5의 FocalLoss+class weight 사고 전례 때문에, 그 사고와 메커니즘이 무관한 Center Loss를 먼저 단독으로, 안전장치(매 epoch rest recall 모니터링)와 함께 시도.
- **구현**: `models_v11.py`에서 forward()가 분류기 직전 attention context 벡터도 반환하도록 확장, 클래스별 학습 가능한 center(50×256)를 두고 CrossEntropy(label_smoothing 0.1) + 0.01×CenterLoss로 v8과 동일 데이터/아키텍처를 처음부터 재학습.
- **안전성 확인**: rest recall이 학습 내내(epoch 1: 97.8% ~ epoch 28: 91.5%) 건강하게 유지됨 — v3~v5의 0.0001~0.0002와는 전혀 다른 양상. Center Loss는 "쉬운 샘플의 손실을 깎는" 메커니즘이 없어 이론적으로도 rest를 억제할 이유가 없었는데, 실측으로도 확인됨.
- **결과 — 효과 없음**: test accuracy 68.64%, macro-F1 57.04% (v8: 68.69%/56.92% — 차이는 측정 잡음 수준). 가장 약했던 E2 그룹(클래스 18~40)만 따로 봐도 평균 F1 변화 +0.005로 거의 없었음. "비슷한 제스처를 더 잘 구분하게 만든다"는 기대 효과가 측정되지 않음.
- **교훈**: v10(가설이 틀림)과 v11(가설 방향은 그럴듯하나 이번 설정에서 측정 가능한 효과 없음)은 다른 종류의 음성 결과다 — v11은 "이 방법은 안 된다"가 아니라 "이 lambda(0.01) 값에서는 효과가 안 보였다"로 정확하게 기록해야 한다. lambda를 사전에 스윕하지 않고 직관으로 고른 값 하나만 시도한 것이 이번 실험의 한계로 남음.

## 16. v12 — 모델 학습 없이 "어려운 피험자"의 정체를 진단
- **배경**: v9~v11에서 학습 전략(시차보정, freeze, center loss) 세 가지가 전부 막힌 길로 끝났는데, 공통적으로 "어떤 전략을 쓰든 S01/S05/S40은 항상 잘 되고 S28/S31은 항상 안 된다"는 패턴이 반복됐다. 모델 쪽을 더 바꿔봐야 할지 의심이 들어, 처음으로 모델 학습 없이 신호 자체를 직접 진단하기로 함.
- **방법**: `diagnose_subjects.py`로 피험자별 정규화 적용 전(원본 필터링 신호)에서 SNR(움직임/rest RMS 비율), channel_cv(채널별 RMS 변동계수, 전극불량 가설), separability_score(50클래스 간 MAV의 ANOVA F값) 세 지표를 40명 전체에 대해 계산, v9의 피험자별 base_acc와 피어슨 상관 분석.
- **결과**: separability_score(r=+0.749, p=2.8e-08)와 SNR(r=+0.700, p=4.9e-07) 모두 매우 강하고 통계적으로 명확한 상관관계. 반면 channel_cv(전극불량 가설)는 r=0.021로 관계 없음 — 가장 직관적이었던 가설(특정 전극이 고장났다)이 가장 먼저 기각됨.
- **핵심 발견**: 어려운 피험자(S28, S31 등)는 전극 결함이 아니라 **근전도 신호 자체가 약하고(낮은 SNR) 동작 간 신호 패턴 차이가 본질적으로 작은(낮은 separability)** 사람들이었다. 이는 전처리/모델로 고치기 어려운 생체신호 자체의 한계에 가까운 원인이다.
- **이번 버전이 특별했던 점**: v1~v11 중 처음으로 GPU/모델 학습이 전혀 없었던 버전. 비용(40명 분석에 ~850초, CPU만 사용)이 지금까지 중 가장 낮았는데도, v9~v11 세 번의 학습 실험보다 더 명확하고 실행 가능한 정보를 얻었다 — "학습을 더 돌리기 전에 데이터를 먼저 들여다보는" 순서가 옳았다는 것을 보여준 사례.
- **한계 → 바로 이어서 해소**: SNR과 separability가 독립적인지를 같은 날 편상관/다중회귀로 추가 분석. 결과: 둘 자체가 r=+0.738(p=5.5e-08)로 강하게 얽혀 있고, separability가 SNR을 통제해도 영향력이 크게 유지되는 반면(0.749→0.482) SNR은 separability를 통제하면 크게 줄어듦(0.700→0.330) — separability가 더 근본적인 변수이고 SNR의 영향은 상당 부분 separability를 통한 간접 효과로 해석됨. 다중회귀 결합 R²(0.608)도 separability 단독(0.561)보다 +4.7%p밖에 안 늘어나 두 지표가 사실상 비슷한 정보를 담고 있음을 확인.

## 17. v13 — 웨이블릿 디노이징, 상관관계를 인과관계로 오해할 위험을 실측으로 확인
- **배경**: v12에서 "SNR을 개선하면 separability도 같이 좋아질 가능성이 있다"는 제안이 나와, 이를 직접 검증하기 위해 웨이블릿 디노이징(`data_utils.wavelet_denoise()`, db4, 4레벨, soft-threshold)을 적용한 신호로 SNR/separability를 다시 계산해 비교. 본 학습 전에 모델 재학습 없이 진단만 먼저 하는 v9~v12의 패턴을 그대로 유지.
- **새 패키지 설치**: PyWavelets(pywt)가 사전에 설치돼 있지 않아 `pip install`로 새로 설치 — 이번 프로젝트에서 처음으로 추가한 외부 패키지. 별다른 버전 충돌 없이 정상 설치됨.
- **결과 — 가설 기각**: SNR은 거의 모든 피험자에서 개선(+0.64dB 평균)됐지만, separability는 거의 모든 피험자에서 악화(-1.99 평균)됨. 어려운 5명(S28,S31,S04,S26,S07)이 SNR을 조금 더 크게 얻었지만(+0.77 vs +0.62dB) 그 차이는 미미했고 separability 악화는 동일하게 나타남.
- **핵심 교훈**: v12에서 관찰한 SNR↔separability의 강한 상관관계(r=0.738)는 **사람들 사이의 자연스러운 차이를 반영한 상관관계였을 뿐, 한쪽을 인위적으로 조작(디노이징)하면 다른 쪽이 따라오는 인과관계는 아니었다.** 디노이징이 잡음으로 간주해 깎아낸 신호 성분 중 일부가 실제로는 클래스 구분에 쓰이던 유용한 정보였을 가능성이 높다 — "상관관계가 있다고 해서 한쪽을 조작하면 다른 쪽도 개선된다"고 가정하면 안 된다는, 통계적으로 흔히 경고되는 함정을 직접 실측으로 확인한 사례.
- **비용 효율**: 진단(CPU, 수 분)에서 역효과가 명확히 드러나 GPU 모델 재학습(1시간 이상)으로는 진행하지 않음 — 만약 진단을 생략하고 곧장 재학습했다면 같은 결론에 도달하는 데 훨씬 큰 비용이 들었을 것.

## 18. v14 — 클래스 그룹화, 이 프로젝트 첫 부분적 긍정 신호
- **배경**: v13(디노이징 기각) 이후, v12부터 미뤄둔 "separability 낮은 피험자에게 클래스 단순화 태스크 적용" 후보를 검증. v8 체크포인트로 test set 추론을 1회만 수행(재학습 없음, 정확도 68.69%로 v8과 정확히 일치하는 것을 먼저 확인해 추론 파이프라인 검증), confusion matrix 기반 계층적 클러스터링으로 50개 클래스를 10/15/20/25개 상위 클래스로 묶어 정확도 재계산.
- **결과**: 클래스를 단순화할수록(k를 줄일수록) 어려운 5명(S28,S31,S04,S26,S07)과 나머지 35명의 정확도 격차가 꾸준히 줄어듦 — 50클래스 12.77p → k=10에서 8.19p(35.8% 감소). 어려운 피험자가 절대 수치로도 더 크게 개선(+21.23p vs 나머지 +16.65p).
- **부분적 결론**: 격차가 완전히 사라지지는 않아(k=10에서도 8.19p 잔존), 어려운 피험자 문제의 약 1/3은 "같은 운동 계열 내 세부 구분 어려움"으로 설명되지만 나머지 2/3는 더 근본적인 원인(v12에서 본 낮은 SNR/separability)으로 남는다. k=10 클러스터링이 실제로 E3(라벨 41~49)를 깨끗하게 독립 클러스터로 분리하는 등 운동 세트(Exercise) 구조와 의미 있게 일치 — 클러스터링이 무작위가 아니라 실제 신호 구조를 반영했다는 신뢰도 확인.
- **의의**: v9(시차보정), v10(freeze), v11(center loss), v13(디노이징) 네 번의 시도가 전부 무효 또는 역효과였던 것과 대조적으로, v14는 이 프로젝트에서 처음으로 부분적으로나마 명확한 긍정 신호를 보인 분석. 다만 사후 그룹화 추정이라 실제 k=10 분류기를 처음부터 학습시켜야 재현되는지 확인 가능 — 다음 단계로 명확히 이어짐.
- **한계**: k를 4개 값(10/15/20/25)만 시도해 격차 감소가 완만해지는 지점을 정밀하게 찾지는 못함 — 빠른 진단이 목적이라 충분하다고 판단했으나 더 세밀한 스캔(5~35)이 남은 과제.

## 19. v15 — v14 사후 추정을 실제 학습으로 검증, 그 과정에서 옛 버그 재발견
- **배경**: v14는 기존 50클래스 모델의 예측을 사후에 그룹화한 추정이었으므로, 처음부터 10클래스로 학습시켜도 같은 효과가 나오는지 직접 검증.
- **버그 재발생**: v14의 cluster_assignment(0~49 인덱스)를 v8 데이터의 raw y_train(실제로는 0-17/35-57/81-89로 불연속)에 바로 적용하려다 IndexError 발생. 원본 라벨이 0-49 연속이 아니라는 사실은 v1 시점에 이미 한 번 발견·문서화했던 것인데, v15 코드 작성 시 그 사실을 깜빡하고 놓쳤다가 에러로 다시 상기함. LabelEncoder로 먼저 0-49 연속 인코딩한 뒤 cluster_assignment를 적용하도록 수정해 해결.
- **교훈**: 한 번 문서화하고 해결한 문제도 시간이 지나면 다시 같은 실수로 이어질 수 있다 — 다행히 이번엔 조용히 잘못된 결과를 내는 대신 명확한 IndexError로 즉시 드러나 바로 잡을 수 있었다. (이런 "조용한 실패" 위험이 있는 지점은 가능하면 assert나 명시적 체크를 코드에 남겨두는 것이 더 안전하다는 점을 기록.)
- **결과 — 검증 성공**: 전체 acc 86.03%(추정 85.92%), 어려운 5명 79.27%(추정 78.75%), 나머지 86.99%(추정 86.94%), 격차 7.72p(추정 8.19p) — 모든 지표가 v14 추정과 0.1~0.5%p 이내로 일치, 오히려 실제 학습이 추정보다 살짝 더 좋음.
- **해석**: v8(50클래스) 모델이 이미 상위클래스 수준의 구조를 충분히 학습하고 있었다는 뜻 — "처음부터 더 쉬운 클래스 수로 학습"이 주는 추가 이점이 크지 않았음. v14의 사후 그룹화 추정 방법론 자체가 이번 케이스에서 신뢰할 만했다는 것도 같이 확인됨.
- **부작용 발견**: confusion matrix에서 클러스터링으로 만들어진 가장 큰 클러스터(약 30만 윈도우, 다른 클러스터의 2~20배 크기)가 다른 클러스터들의 오분류를 흡수하는 "흡수 클래스"처럼 작동 — 클러스터 크기가 균등하지 않은 클러스터링의 부작용으로, 다음 버전에서 다룰 후보로 기록.

## 20. v16 — 2단계 계층적 분류기, 가설은 맞았지만 조립 방식이 틀림
- **배경**: v15가 "10클래스 문제"에서는 효과를 보였지만 그 자체로는 50개 원래 동작을 구분해야 하는 응용에 못 쓴다. 1단계(상위클래스 예측, v15 재사용) → 2단계(클러스터 내부 fine label 예측, 클러스터별 서브 분류기 9개 신규 학습)로 이어지는 하드 라우팅 캐스케이드를 구성해 50클래스 전체 기준으로 v8과 비교.
- **결과**: 전체 acc 68.02%(v8 68.69%보다 -0.67p), 어려운 5명 56.04%(v8 57.52%보다 **-1.48p, 더 나빠짐**), 격차 13.68p(v8 12.77p보다 **+0.91p, 더 벌어짐**) — 기대와 정반대.
- **원인 분해**: (1) 1단계 라우팅 실수는 2단계가 절대 복구 불가능(클러스터가 서로 안 겹쳐서 잘못 보내지면 100% 오답) — 캐스케이드 분류기의 잘 알려진 구조적 약점을 직접 확인. (2) 어려운 피험자는 1단계 정확도 자체가 더 낮음(79.27% vs 86.99%, v15에서 이미 확인된 수치). (3) 1단계가 맞아도 2단계 내부에서 어려운 피험자 정확도가 여전히 낮음(약 70.7% vs 80.2% 추정) — 최종 정확도가 두 단계 정확도의 곱에 가까워 오차가 누적·증폭됨.
- **비용 측면 재확인**: 클러스터 9(20클래스, rest 포함, 거대 흡수 클래스) 서브 분류기 학습만 49분(전체 stage-2 학습 시간 70분의 70%) — v15에서 본 "흡수 클래스" 부작용이 학습 비용에도 그대로 비례해서 나타남, 사전에 "다른 클러스터보다 오래 걸릴 것"으로는 예상했지만 v8 전체 학습과 맞먹는 수준일 줄은 가늠하지 못함.
- **교훈**: v9~v11/v13(가설 자체가 틀림)과 다른 종류의 음성 결과 — v14/v15에서 본 "클래스 단순화 효과"는 상위클래스 문제 자체에는 진짜였지만, 하드 캐스케이드로 조립하는 과정(부분의 합)에서 사라졌다. "부분이 좋다고 전체 시스템이 좋아지는 것은 아니다"라는, 시스템을 합성할 때 흔히 나오는 함정을 직접 확인한 사례. 다음 시도(소프트 라우팅)로 자연스럽게 이어짐.

## 21. v17 — 소프트 라우팅, 방향은 맞지만 v8을 넘지 못함
- **배경**: v16의 핵심 약점("1단계 라우팅 실수는 2단계가 복구 불가")을 완화하기 위해, v15(1단계)/v16(2단계) 체크포인트를 재학습 없이 재사용하고 추론 방식만 혼합 전문가(mixture of experts) 방식으로 변경 — 1단계의 클러스터별 확률을 그대로 살려 모든 클러스터 전문가의 의견을 가중 합산.
- **결과**: 모든 지표에서 v16(하드 라우팅)보다 일관되게 개선(전체 acc +0.17p, 어려운 5명 +0.29p, 격차 13.68p→13.55p) — "복구 기회를 주면 도움된다"는 메커니즘이 실제로 작동함을 확인. 다만 v8(단일 50클래스, 68.69%/56.92%)에는 여전히 못 미침.
- **원인**: 클러스터 9(20클래스, rest 포함)의 테스트셋 평균 가중치가 0.62로 압도적 — 상대적으로 부정확한(val F1 0.556) 이 전문가의 의견이 거의 모든 윈도우에 막대한 영향력을 행사해 소프트 믹싱의 효과를 희석시킴. v15부터 계속 지적된 "거대 흡수 클러스터" 문제가 소프트 라우팅에서도 동일하게 부작용의 핵심 원인으로 재확인됨.
- **작은 도구 사용 착오**: 평가 스크립트를 `python3 evaluate_v17.py | tail -40`으로 실행했는데, `tail`이 `-f` 없이는 입력 파이프가 끝날 때까지(프로세스 종료까지) 아무것도 출력하지 않는다는 걸 깜빡해 중간에 "로그가 안 찍힌다"고 잠시 혼란이 있었음. 실제로는 정상 진행 중이었고 완료 후 전체 로그가 한꺼번에 나왔다 — 파이프/리다이렉션 버퍼링 동작을 사전에 챙겨야 한다는 흔한 함정.
- **흐름 정리**: v14(가설 성공, 클래스 단순화) → v16(조립 실패, 하드 캐스케이드) → v17(조립 개선, 소프트 라우팅이지만 부족) — 세 버전 모두 "거대 흡수 클러스터"라는 동일한 약점에 발목 잡힘. 이 약점을 직접 해결(클러스터 9 재세분화)하거나, 계층적 분류 계열 자체를 보류하고 다른 방향(피험자별 fine-tuning, 도메인 적응)으로 우선 전환하는 두 갈래 선택지가 남음.
